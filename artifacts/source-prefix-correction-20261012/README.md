## Cache producer double rounding

The independent-state audit finds **99** values across the six K/V cache pairs through decode 27 where nearest F32 materialization followed by nearest-even F16 differs from direct nearest-even F16. This can occur even when the F32 producer is perfectly rounded. One value is −0.5773926053439227: nearest F32 is −0.577392578125, whose F16 tie rounds to −0.5771484375; direct F64-to-F16 rounds to −0.57763671875. A midpoint regression reproduces this without a model.

Three explicitly counterfactual CPU controls first reproduce every approved vector exactly, then retain all F64 equations except the specified F32 producer materialization before cache storage. They never replace the evaluator or target. Across the 51 long-request prefixes, inserting this rounding for both K/V fails **10/51**, maximum **0.002070783644**, RMS **0.000171973405**; K only fails **14/51**, maximum **0.002493214128**, RMS **0.000186641388**; V only fails **3/51**, maximum **0.001531386069**, RMS **0.000100909751**. The both-control worst step is 28, also the worst prefix of the preceding physical candidate.

This establishes a concrete materialization contribution and cancellation between error sources. It is **not a proof that no F32 implementation can pass the final-logit tolerance**, and it is not permission to change the approved target. A corrective implementation must preserve the producer's rounding information until F16 packing or equivalently fuse that boundary. Choosing whichever rounded cache value happens to fit retained logits would not be a valid correction. The existing direct-F16 cache/fused-normalization path is the next implementation boundary to evaluate; no such runtime change is yet qualified.
