# Execution backend privacy boundary

Ordinary Doppler inference executes plaintext locally. The ordinary activation frames, resident publication records and generation/inspection evidence can contain tokens, text, activations and deterministic plaintext-derived fingerprints. Partitioning or transport encryption does not turn these computations into encrypted inference.

`src/inference/execution-backend-contract.js` supplies a versioned backend descriptor, exact model support checking and state namespace contract. The matching declaration specifies the distinct client preparation, evidence verification, sealing, evaluator execution, client finalization and disposal operations required of a future extension. Only plaintext descriptors can pass the current availability gate. Attested and cryptographic advertisements cannot enable a backend, and a model unsupported by that descriptor fails before dispatch.

## Direction for the protected tier

Owner decision, 2026-11-17: a protected backend must leave the requester light. The requester verifies evidence, encrypts its request and decrypts the answer; it holds no weights and runs no model operation. The `attested` kind is therefore the first protected tier to build. The `cryptographic` kind stays in the contract for approaches that meet the same requirement, and the hybrid GLWE experiments below, which make the requester run every non-linear step, are retained as research and are not being extended to Flash.

The [attested light-client route](../tools/privacy-attested/README.md) implements the six extension operations for `doppler-attested-session/v1`: AMD SEV-SNP evidence appraisal against pinned roots, a report-data binding of model, key, attempt, state namespace and session policy checked before any request byte is encoded, and an authenticated encrypted stream. Its verifier accepts genuine AMD reports from public test data. The complete protocol has run only against a software stand-in for the hardware, no confidential guest exists in the fleet, and the installed trust policy admits no deployment. The availability gate is unchanged.

No attestation verifier or cryptographic inference backend is shipped or qualified in the runtime. The interface is scaffolding for implementations, not a security proof or an encrypted-inference implementation. Such implementations need an explicit adversary/collusion model, concrete protocol and parameters, exact leakage (including lengths, timing, routing and MoE accesses), trusted client operations/key handling, model identity, lifecycle tests and independent review. Hardware attestation additionally requires real endorsement/measurement/freshness and channel binding validation. Do not advertise either guarantee until the implementation and evidence exist.

`src/client/model-host/privacy-receipt.js` provides a separate whitelist projection for provider-safe authorization metadata. It excludes text, token IDs, transcripts, arbitrary stats/errors and input/output fingerprints. Its receipt ID hashes only this metadata. Confidentiality, integrity and availability proof fields are explicitly false: a record is not proof of any of those properties. The ordinary local generation-evidence API and inference path retain their existing behavior and overhead.

`executionStateNamespace` binds model, backend, tenant, session, policy, route and key context without prompt/output fingerprints. Hosts must actually use the resulting namespace when retaining state; the helper alone does not isolate an external cache or guarantee remote erasure. Reploid independently namespaces its existing resident conversation contexts using the full request policy, exact route and authenticated tenant.

Focused validation: `node tests/inference/execution-backend-contract.test.js`, `npm run typecheck:source`, and `npm run check:fast`. Existing activation corruption and resident publication tests remain independent integrity checks. No GPU speed, numerical qualification, physical TEE or cryptographic security claim follows from these checks.

An isolated [BFV autoregressive protocol experiment](../tools/privacy-demo/README.md) uses pinned node-seal 7.0.0/Microsoft SEAL in separate client/evaluator processes. Its client decrypts and selects each token, then reencrypts the next input; four steps match an eight-symbol bigram reference without plaintext feedback. It reports actual timing and traffic; noise-budget queries are restricted to ciphertexts verified by the full replay mode. It is not a shipped backend, supported transformer model, independent review or malicious-adversary guarantee. A focused test demonstrates that a valid substituted ciphertext can produce incorrect feedback, and production cryptographic profiles stay unavailable. Model-specific attention/decoding, malicious-security/leakage analysis, validated parameters/keys, endpoint binding and independent review remain blockers.


The experiment additionally offers an explicitly charged full-client reference audit of its tiny score vector. It detects incorrect computation but is not a cryptographic proof or an efficient outsourcing verifier. A separate adversarial test homomorphically perturbs responses using only public evaluation keys and wire ciphertexts: the audited client stops for one private seed and continues for another, exposing a selective-failure predicate. This is concrete evidence that its active-adversary privacy is insufficient, even with stronger local correctness checks. No production privacy qualification follows from the new integrity audit.

The BFV experiment now defaults to public ciphertext replay: the client repeats the full deterministic encrypted circuit and requires exact ciphertext equality before any response decryption or secret-key-dependent noise-budget query. Tests show the same selective-failure modification rejected for every seed, without decrypting the modified response. This charges the full encrypted computation to the client and provides no outsourcing saving or succinct proof. The deliberately unsafe modes retain the negative tests. This fixture improvement does not open the runtime gate or establish independent cryptographic review.

A separate [Concrete GLWE transformer experiment](../tools/privacy-concrete/README.md) now implements an actual serialized client/evaluator boundary for pinned `sshleifer/tiny-gpt2`. The client owns keys, attention, nonlinearities, masks and decoding; a fresh CPU evaluator receives public matrices/evaluation material and ciphertexts for all eight transformer projections over four autoregressive steps. No plaintext activation or token feedback is sent. Exact public encrypted replay precedes response decryption; altered valid computations reject independently of plaintext equality. Replay repeats all encrypted work locally and is not an outsourcing saving or succinct proof. Its model is a two-hidden-dimension test checkpoint, not full GPT-2, and its pipe transport is not a qualified network deployment. Numerical, traffic and timing evidence belongs to that exact fixture and protocol. Production descriptors remain unavailable pending reviewed adversary/leakage/side-channel/implementation guarantees and actual backend qualification.

The [small-Qwen experiment](../tools/privacy-concrete/QWEN.md) extends this boundary to the exact official Qwen2.5-0.5B-Instruct checkpoint. Complete client-side generation uses one homomorphically evaluated key-projection matrix product over four steps, with exact model/quantized-weight/rectangular-shape profile admission and public replay before decryption. All other model operations remain client-owned; this is not full encrypted model execution or production malicious security. The retained source-tensor audit identifies wider projections that exceed the current conservative arithmetic budget, including Flash hidden-width products. Unsupported installed profiles and numerical ranges fail before private payload. No runtime capability advertisement or availability gate changed.
